## 3. CRUD endpoints（落實「API 路由設計：mount 在 meeting 下」「Ownership 驗證：兩端 meeting 都必須屬於 current user」）

- [x] 3.1 在 `packages/backend/meeting_playbook/meeting_links/router.py` 定義 FastAPI APIRouter，掛 `GET /api/meetings/{id}/links`，**行為**：透過 `X-User-Id` 取得 current user → 驗 `id` 是該 user 的 meeting（不存在或不屬於 user 一律回 HTTP 404 `meeting.not_found`，不洩漏存在性）→ 呼叫 `list_for_meeting(id)` 回 `{"links": [MeetingLinkView, ...]}`，sort `created_at DESC`。本 task 落實 requirement「`GET /api/meetings/{id}/links` returns bidirectional related links for the meeting」。**驗證**：新測 `packages/backend/tests/meeting_links/test_router.py` 紅燈兩條：(a) user U1 對自己擁有的 A 拿到 list；(b) user U2 對 U1 擁有的 A 發 GET 拿到 404 + `meeting.not_found`，落實 spec scenarios 「User views related links for their own meeting」「Ownership isolation hides another user's meeting」。
- [x] 3.2 在同檔掛 `POST /api/meetings/{id}/links` body `{"to_meeting_id": UUID}`，**行為**：驗 `id` 與 `to_meeting_id` 兩個 meeting 都屬於 current user（任一不通過回 HTTP 404 `meeting.not_found`）→ `to_meeting_id == id` 回 HTTP 422 `meeting_link.self_reference` → 呼叫 `repository.create(id, to_meeting_id)`；catch `MeetingLinkDuplicate` 回 HTTP 409 `meeting_link.duplicate`；catch `MeetingLinkSelfReference` 回 HTTP 422 `meeting_link.self_reference`；成功回 HTTP 201 `{"link_id": UUID}`。本 task 落實 requirement「`POST /api/meetings/{id}/links` creates a bidirectional link with duplicate and self-reference guards」。**驗證**：紅燈四條：(a) 新建成功 → 201；(b) 同方向重複 → 409；(c) 反方向重複 → 409；(d) `to_meeting_id == id` → 422，落實 spec scenarios 「First-time link creation succeeds」「Duplicate link rejected regardless of direction」「Self-reference rejected with 422」。
- [x] 3.3 在同檔掛 `DELETE /api/meetings/{id}/links/{link_id}`，**行為**：呼叫 `repository.get(link_id)` 拿 link 兩端 meeting_id → 確認其中至少一端 meeting 屬於 current user 且其中一端 meeting_id 等於 path 的 `{id}`（多重驗證避免他人 link_id 借自家 meeting_id 路徑使用）→ 通過則 `repository.delete(link_id)` 回 HTTP 204；不通過或 link 不存在統一回 HTTP 404 `meeting_link.not_found`，不洩漏存在性。本 task 落實 requirement「`DELETE /api/meetings/{id}/links/{link_id}` removes the link from either side」。**驗證**：紅燈兩條：(a) owner 從任一端 path 發 DELETE → 204 + row 消失；(b) 另一個 user 拿其他 user 的 link_id 借自家 meeting_id path 發 DELETE → 404 且 row 未刪，落實 spec scenarios 「Either-side delete removes the link once」「Delete on a foreign link returns 404 without leaking existence」。
